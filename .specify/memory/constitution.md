# BananaSlides-GenAI 项目章程

## 核心原则

### I. AI 模型路由抽象

所有 AI 功能必须通过统一的适配器模式接入，禁止直接调用特定模型 API。系统必须支持通过配置切换模型提供商（Gemini、GLM、DeepSeek、本地模型），无需代码变更。

- **MUST**: 所有 AI 调用通过 Router-Adapter 层
- **MUST**: 模型配置支持热切换（无需重启服务）
- **MUST**: 每个适配器实现统一的输入/输出契约
- **MUST NOT**: 业务代码直接依赖特定模型 SDK

**理由**: 保障供应商独立性，实现成本/质量/速度的动态平衡，支持私有化部署场景。

### II. 意图驱动设计

用户意图是系统设计的核心。所有功能必须从用户目标出发，而非技术实现便利性。

- **MUST**: 每个功能都有明确的用户价值主张
- **MUST**: 复杂操作提供一键式简化入口
- **MUST**: 错误消息用用户语言描述，而非技术术语
- **MUST NOT**: 暴露内部技术细节给用户

**理由**: 降低使用门槛，将 PPT 制作从小时级压缩到分钟级，实现真正的"意图即交付"。

### III. 混合架构一致性

前后端技术栈必须保持一致的设计哲学和通信契约。

- **MUST**: REST API 使用统一的错误码和响应格式
- **MUST**: 数据库 Schema 与前端类型定义同步（Prisma + TypeScript）
- **MUST**: 状态管理遵循单一数据源原则
- **MUST**: 组件设计支持响应式和暗色模式

**理由**: React 19 + Express 5 + Prisma 构成全 TypeScript 生态，确保端到端类型安全。

### IV. 全链路可观测性

从用户操作到 AI 生成的每个环节都必须可追踪、可审计。

- **MUST**: 所有关键操作记录结构化日志
- **MUST**: AI 生成任务有唯一追踪 ID
- **MUST**: 项目变更支持版本回溯（快照系统）
- **MUST**: 性能指标（生成耗时、 Token 消耗）自动上报

**理由**: 复杂的 AI 生成链路需要可调试性，快照系统提供"后悔药"，支持资产复用。

### V. 工业级交付标准

代码必须经过验证才能合并，没有例外。

- **MUST**: TypeScript 编译零错误（`noEmit` 检查通过）
- **MUST**: 关键业务逻辑（订单、支付、权限）有单元测试覆盖
- **MUST**: API 变更同步更新前端类型定义
- **MUST NOT**: 使用 `as any` 或 `@ts-ignore` 绕过类型检查

**理由**: 虽然使用模拟支付，但业务流程必须生产就绪；类型安全是大型 TypeScript 项目的生命线。

## 技术栈约束

### 前端架构

- **框架**: React 19.2 + Vite 6.2
- **样式**: Tailwind CSS v4.1（优先使用内置工具类，最小化自定义 CSS）
- **状态**: Tanstack Query v5.9（服务器状态）+ React Context（客户端状态）
- **类型**: TypeScript 5.9（严格模式启用）

### 后端架构

- **运行时**: Node.js 22 LTS
- **框架**: Express v5.2
- **ORM**: Prisma v6.19
- **数据库**: SQLite（开发/单机部署）或 PostgreSQL（生产扩展）
- **认证**: JWT（内存存储，无 Refresh Token）

### AI 集成

- **路由**: 自定义 Router-Adapter 模式
- **支持模型**: Gemini 2.0/1.5、GLM-4.7、DeepSeek、本地 Llama/Qwen
- **文档解析**: MinerU v4（PDF/Word 结构化提取）
- **图像生成**: Gemini-3-Pro-Image、火山引擎 Ark

## 开发工作流程

### 规范驱动开发

1. **需求阶段**: 使用 `.specify/templates/spec-template.md` 编写功能规范
2. **设计阶段**: 使用 `.specify/templates/plan-template.md` 创建实施计划
3. **任务阶段**: 使用 `.specify/templates/tasks-template.md` 拆分原子任务
4. **实现阶段**: 按任务列表实施，每个任务完成后记录实现日志

### 代码审查门控

- 所有 PR 必须通过 TypeScript 编译检查
- 业务逻辑变更必须更新对应的手册文档（`docs/04_Manuals/`）
- 数据库 Schema 变更需要迁移脚本和回滚方案
- 权限相关代码必须对照 `权限体系落地实施方案.md` 验证

### 测试策略

- **单元测试**: 核心服务层（订单、支付、积分、权限）
- **集成测试**: API 端点契约、数据库事务
- **手动验证**: AI 生成效果、UI 交互流程
- **验收测试**: 参考 `docs/05_Testing/用户验收用例集.md`
